# Irodori and Kōbō storage: design proposal

**Draft 2 · 28 October 2026 · revised after the website's review of draft 1
(`IRODORI-STORAGE-REVIEW-DRAFT-1.md`). For the website's agreement before Claude implements saving
to storage.** Uses the **v1.2.1 bridge unchanged** (`status`, `read`, `stat`, `list`, `put` with
conditions, `remove`). Saving to storage needs website work first (§9) and stays off until then.
Section 8 is the Irodori adapter for the v1.4 proposal, which stays pending.

What changed since draft 1: recovery and cache scope (§4), recovery wording (§1, §4), read-only
(§5), the order of a save and lost responses (§3), registry and head validation (§2), previews
inside the committed head (§2), part uploads (§6), names of orphaned documents (§2), website
blockers (§9). Answers to draft 1's questions are in §10.

## 1. What changes for the user

Today the web version opens files from the device and "saves" by downloading. With storage
connected:

- **File ▸ Open from Kōbō…** lists the account's Irodori documents on that storage connection
  (name, size, last changed, a small preview) and opens one.
- **Save** writes back to the same document; **Save As…** creates a new one; **Save a Copy** writes
  a new document and leaves the open one and its save target unchanged. Download (Export) still
  works as before.
- **Recent** lists storage documents first.
- While a document has unsaved changes, Irodori keeps a recovery copy in the browser. This is
  **best effort**: the browser can refuse or clear its storage, and a lost device loses its copies.
  It covers a closed tab or a dropped connection in the usual case; it doesn't replace saving.
- Without storage (guest, or no connection), Irodori works as today, and "Open from Kōbō" is not
  offered.

## 2. Where documents live

The app namespace is `irodori` (root `/Kobo/Irodori/`).

```text
documents.json                    the registry: one entry per document (below)
documents/<uuid>/head.json        commit point of the document's latest version (generations)
documents/<uuid>/gen/<g>/<n>      the version's parts (≤ 1 MiB each, create-only)
```

- A **document** is stored with Hikari's generation mechanism: parts written create-only, then
  `head.json` replaced conditionally (`If-Match`; create-only for a new document). It reuses
  `kobo-sync.js` with `root = documents/<uuid>`.
- **Logical files in a version** (the allowlist): `document.pcraft` (Irodori's own layered format)
  and optionally `preview.png`. The preview is part of the same committed version, so it can never
  show a different save from the head's. There is no separate fixed-name preview file.
- **Size limit:** 256 MiB (268,435,456 bytes) for `document.pcraft`, i.e. at most 256 parts of
  1 MiB. Irodori serializes and measures before uploading or allocating anything for the upload;
  a bigger document isn't saved to storage (the message says so, and Export still works). The
  limit is on the compressed file. Opening checks the decoded size separately (below).
- `<uuid>` is a lower-case v4 UUID generated by the app. Names never appear in paths.

### `documents.json`

```json
{"format": "kobo-irodori-documents", "version": 1, "documents": [
  {"id": "<uuid>", "name": "Snowy River edit", "size": 18342112, "width": 6000, "height": 4000,
   "modified": "2026-10-28T01:02:03Z", "hidden": false}
]}
```

- Limits: at most **1,000 entries and 256 KiB encoded**, both enforced before publishing. When a
  change would exceed either, nothing is published, the work stays open and in recovery, and the
  message gives the cause.
- Validation on every read: unique canonical lower-case v4 ids; names 1–100 code points of plain
  text with no control characters; sizes non-negative safe integers; width and height 1–300,000;
  valid RFC 3339 times. A malformed or corrupt registry is an error the user sees, never replaced
  by an empty one. Registry values are for display only: paths come from validated ids, and sizes
  never decide an allocation.
- Updates are compare-and-swap (`If-Match`) with at most five attempts. Each attempt re-reads,
  validates and re-applies **only this change** (add, rename or hide one entry) to the fresh
  registry, so another device's entries are never overwritten by an old copy.
- An absent registry is created create-only, and only by an explicit Save As or reconciliation on
  a writable connection. Opening never creates one.
- **Renaming and hiding** change only the registry. Deleting documents and cleaning up old
  versions are out of scope.

### `head.json` and opening

Opening validates `head.json` with the existing bounded generation schema: names, paths, counts,
totals and hashes, and the logical-file allowlist above. Before assembling `document.pcraft` it
checks the total against the limit and the memory available. Decoding then checks the image itself
independently (canvas size, layer count, decoded bytes; the `.pcraft` reader's limits). A 256 MiB
compressed file isn't assumed safe to decode. A registry entry whose head is missing shows as
"unavailable" and opens nothing. A missing or invalid preview shows a placeholder.

### Documents found without a registry entry (orphans)

These are rare (a Save As whose registry update never succeeded and whose local journal was lost).
The registry is the normal way to browse, so Open and the Drive page never list folders.
Reconciliation is a separate, explicit action ("Look for unlisted documents"): one `list` of
`documents/` (at most 2,048 direct children, as the providers return), then a head check for each
unknown valid id. Each one found is registered as **"Recovered document <first 8 of uuid>"** (the
name is in the registry only, so it can't be recovered). Reconciliation stops at the listing limit
and says so.

## 3. Saving, in order

**Save (existing document):**
1. Serialize. Measure against the limit. Compare the SHA-256 of `document.pcraft` with the last
   synced version's (from its head's logical list). If unchanged, nothing is uploaded, and only
   time stamps or view state differing doesn't count as a change. (To be verified when this is
   built: that the `.pcraft` writer gives the same bytes for an unchanged document. If it doesn't,
   the comparison uses the bundle's per-entry content hashes and leaves out time stamps and view
   state.)
2. Upload changed parts (§6), then commit `head.json` conditionally on the last synced head ETag.
3. Update the registry entry (size, dimensions, modified) by CAS, as above.

**Save As / Save a Copy (new document):** new UUID; parts and preview first; `head.json`
**create-only** last; then the registry entry (CAS). Save a Copy leaves the open document and its
save target as they were.

**Lost responses and partial success.** A save is reported as successful only once it is
verified:
- After a commit whose response was lost (timeout, offline), Irodori re-reads `head.json` and
  checks generation, size and the content hash against what it sent. If they match, the save
  landed. If not, it did not. A retry uses **the same UUID and generation**. It never creates
  another UUID, and never writes over a head it didn't verify as its own.
- If the head is committed but the registry update fails, the message is "Saved; the document list
  will be updated", and a reconciliation journal (scoped as in §4) retries that registry change
  for the same UUID until it succeeds or the user removes it.
- An upload alone, or an attempted registry write, is never treated as proof that a save happened.

**Conflicts.** The conditional head write fails because another device saved first. Irodori keeps
the work open and in recovery and offers:
- **Save as a copy (recommended):** a new document (Save As above), "<name> (this device's copy)".
- **Replace with mine:** only after the user picks it. Irodori reads the current head fresh and
  makes one conditional commit against that exact version. If another save gets in between, the
  conflict choice appears again. Irodori never keeps retrying on its own.
- **Cancel:** nothing saved. The work stays open and in recovery.

There is no clock-based winner and no silent overwrite.

## 4. Browser storage (scopes, recovery, cache)

Scope: **account + storage connection + app + document**. The guest is separate. Nothing moves
between scopes.

| What | Scope (folder in the browser's private storage) |
|---|---|
| Preferences, brush presets | account (`irodori.preferences.user-<h>`, `irodori.presets.user-<h>`); the guest keeps its existing names |
| Recovery copies | `recovery-guest`; signed in with no connection `recovery-user-<h(user)>`; with a connection `recovery-kobo-<h(user, connection)>`; inside, one entry per document |
| Cache of documents opened from storage (planned) | `cache-kobo-<h(user, connection)>/<uuid>/…` |
| Upload and registry journals (planned) | `journal-kobo-<h(user, connection)>/<uuid>/…` |

`<h>` is a hash, so user keys and connection ids never appear in names. A change of account or
connection while Irodori is open is announced. The open documents stay with the account and
connection they were opened under, until the user saves or downloads and reopens Irodori.

**Recovery copies** (implemented now, before storage, in this build):
- A copy is written about 10 seconds after a document's changes pause, at once when the tab is
  hidden or closing, and on the app's own autosave schedule. A copy has a description beside it
  (name, last-saved path, time, session).
- It's removed only after the document is saved or closed, or after an explicit Discard. A
  download doesn't count as a save (a download may not land).
- At the next launch, copies are reopened, newest first, up to 1 GiB in total. Larger leftovers
  stay where they are and are reported.
- Several tabs: each tab holds a Web Lock for its session, and a tab never takes or removes another
  running tab's copies.
- Irodori asks the browser for persistent storage. It may refuse. Recovery copies are never
  cleared to make room.
- Once saving to storage exists, a document with unsaved or conflicted changes keeps its recovery
  copy (a durable "dirty branch") until a **verified** save (§3) or an explicit Discard.

**Cache** (with saving to storage): budget from `navigator.storage.estimate()`, conservatively at
most 25% of the remaining quota and never more than 1 GiB. Only clean entries are evicted (least
recently used), because they can be fetched again. Each is re-checked against the head ETag before
use.

## 5. Read-only connections

A read-only connection (for example Google's competing-write gate) means **no `put` at all on that
connection**: Save, Save As, Save a Copy and registry changes are disabled, with the reason shown.
Open, Export (download), and recovery copies in the browser keep working. Saving somewhere else
needs an explicit destination on a verified writable connection, once connection targeting
exists. There is no automatic switch to another provider.

## 6. Uploads

- Two part uploads at a time (the shell allows four; Irodori starts at two and may go to four
  after measurement), with bounded, jittered backoff that follows `retryAfterMs`.
- Progress of an interrupted upload is kept per scope (§4), so a save resumes rather than
  restarts.
- No promised save time. A small edit can change most parts of a compressed `.pcraft`, so reuse
  of unchanged parts is measured, not assumed.
- Acceptance before enabling: 200–250 MiB real documents, interrupted and resumed, and two
  devices competing, on both providers. Verify whole-file hashes, and record throughput, 429s and
  retries.

## 7. Status and errors

The top bar shows the document's state: **Saved to storage · Google Drive**, **Saving…** (bytes),
**Saved; list update pending**, **Not saved: <reason>**. A failed save never closes the document
or removes its recovery copy.

## 8. Adapter for bridge v1.4 (pending agreement)

| v1.4 item | Irodori |
|---|---|
| Drive listing | the validated registry's entries that aren't hidden: name, size, dimensions, modified (display only), and the committed version's `preview.png` if present (validated PNG, bounded bytes and dimensions, served as a private blob or `image/png` with nosniff). Never `head.json`, `gen/` or parts. |
| `open.path` | exactly `documents/<uuid>`, validated by the website and the app, with fresh app and connection authorization. A missing document shows "No longer available" and creates, copies or selects nothing else. |
| `prepare-to-leave` | **busy** while a save, an upload or a registry update is running, or a conflict is unresolved. **Unsaved edits:** busy, with the app action **Save and switch**. Only after a **successful** recovery write, and with the user's consent, may Irodori reply **ready** with `pending: ["unsaved-recovered"]`, a receipt bound to the request and to this account, connection and document. If the recovery write fails, it stays busy and offers Export. |
| Quiescent after ready | no edits, saves or registry writes until cancel or teardown. Sign-out or revocation tears down at once. |

## 9. Website work before saving to storage is switched on (from the review)

1. **Registry checkpoints:** the backup trigger covers `documents.json` as well as `head.json` and
   `libraries.json`, so a name, rename or hide after a head is captured. Test: a full lost-index
   restore of several documents, with names, hidden flags, previews and original bytes.
2. **Index backup capacity:** today about 4,096 records and 2 MiB per app and connection,
   including retained generations. Before enabling, either incremental or chunked index backup is
   agreed and tested, or Irodori enforces a much smaller app-wide budget that the website gives
   (for example a maximum number of documents × versions kept). Irodori won't work around the
   checkpoint guard.
3. The website Drive page and the v1.4 reader stay proposals.

## 10. Answers from the review (agreed)

1. Normal browsing uses the registry plus head checks. `list` is only for explicit, bounded
   reconciliation (§2).
2. Many sequential ≤ 1 MiB puts are fine, but there's no certified time or quota: two to four
   concurrent, and measure (§6).
3. Previews are private, part of the committed version, and validated as untrusted PNG (§2, §8).
