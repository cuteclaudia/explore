# Irodori and Kōbō storage: design proposal

**Draft 1 · 28 October 2026 · for ChatGPT's review (website side) before Claude implements it.**
Uses the **v1.2.1 bridge unchanged** (`status`, `read`, `stat`, `list`, `put` with conditions,
`remove`). Nothing here needs a new website operation. Section 6 is the Irodori adapter that the
v1.4 draft (app switcher and Drive) asked each app to define.

## 1. What changes for the user

Today the web version opens files from the device and "saves" by downloading. With storage
connected:

- **File ▸ Open from Kōbō…** lists the account's Irodori documents (name, size, last changed, a
  small preview) and opens one.
- **Save** writes back to the same document; **Save As…** creates a new one; **Save a Copy** keeps
  the open document unchanged. Download (Export) still works as before.
- **Recent** lists storage documents first.
- While a document is open, work is kept in the browser too (crash recovery), so a closed tab or a
  lost connection loses nothing.
- Without storage (guest, or no connection), Irodori works as today, and "Open from Kōbō" is not
  offered.

## 2. Where documents live (§6, §9)

The app namespace is `irodori` (root `/Kobo/Irodori/`, as Hikari's is `/Kobo/Hikari/`).

```text
documents.json                    the registry: one entry per document (below)
documents/<uuid>/head.json        commit point of the document's latest version (§7 generations)
documents/<uuid>/gen/<g>/<n>      the document's parts (≤ 1 MiB each, create-only)
documents/<uuid>/preview.png      small preview for Open and Drive (≤ 256 px, ≤ 128 KiB), optional
```

- A **document** is stored with the same generation mechanism Hikari's library uses (§7, §7a):
  new parts are written create-only, then `head.json` is replaced conditionally (`If-Match`).
  That reuses `kobo-sync.js` as tested, with `root = documents/<uuid>`, so a document is never
  half-written and a competing save is detected.
- **Logical file:** one file per document, `document.pcraft` (Irodori's own layered format). A PSD
  or image the user opens from storage is converted to `.pcraft` on first save; Export still
  produces PSD, PNG, JPEG and so on as downloads.
- **Size limit:** 256 MiB per document (`MAX_LIBRARY_BYTES`), checked before reading anything into
  memory. Bigger documents stay in the browser and can be exported. The message says so.
- `<uuid>` is generated by the app (lower-case v4). Names never appear in paths, so renaming
  touches only the registry, and odd characters in names are harmless.

### `documents.json` (≤ 256 KiB, ≤ 1000 entries, updated by CAS with 5 retries, like `libraries.json`)

```json
{"format": "kobo-irodori-documents", "version": 1, "documents": [
  {"id": "<uuid>", "name": "Snowy River edit", "size": 18342112, "width": 6000, "height": 4000,
   "modified": "2026-10-28T01:02:03Z", "hidden": false}
]}
```

Names are 1–100 code points of plain text. `size`, `width`, `height` and `modified` are for display
only, and the document's `head.json` is the truth. A registry entry whose `head.json` is missing
shows as "unavailable", never as an empty document. A head without an entry, for example after
an interrupted Save As, is re-registered by the app the next time it lists documents.

## 3. Conflicts (as in Hikari 0.16.0, §10a)

Two devices saving the same document: the second save's conditional `head.json` write fails.
The app keeps the user's work open and offers:

- **Save as a copy (recommended):** the user's version becomes a new document,
  "<name> (this device's copy)".
- **Replace with mine:** a new version, committed conditionally on the *current* head.
- **Cancel:** nothing is saved yet. The work stays open and is kept in browser recovery.

Content comparison (SHA-256 against the last-synced head) avoids false conflicts, as in Hikari. No
clock-based winner, no silent overwrite.

## 4. Browser storage (§9, §9a)

- Per account, as in Hikari: `doc-<hash>/` folders in OPFS, never shared between accounts or with
  the guest.
- **Recovery copy** of each open document, written a few seconds after changes. On the next
  launch, recovered documents are offered ("Restore unsaved changes?"). They're deleted only after
  a successful save or an explicit "Discard".
- **Cache** of documents opened from storage, so reopening is quick. It's evicted
  least-recently-used past a budget (default 1 GiB) and always re-checked against the head ETag
  before use.

## 5. Status and errors

The top bar shows the document's state: **Saved to storage · Google Drive**, **Saving…** (bytes),
**Not saved: <reason>**. A failed save never loses the document. It stays open and in recovery.
A read-only connection (Google's competing-write gate) disables Save and shows why. Open, Save As
and Export still work.

## 6. Adapter for bridge v1.4 (app switcher and Drive)

| v1.4 item | Irodori |
|---|---|
| Drive listing | `documents.json` entries not hidden: name, size, dimensions, modified, `preview.png` if present. Never list `head.json`, `gen/` or parts. |
| `open.path` | exactly `documents/<uuid>` (lower-case v4). The app checks the registry and `head.json`. A missing document shows "No longer available" and creates nothing. |
| `prepare-to-leave` | **busy** while a save/commit or registry update is in progress ("Saving Snowy River edit"). **Unsaved edits:** busy with reason "Unsaved changes in <name>" and an app action **Save and switch**. Edits are already durable in browser recovery, so with the user's consent the app may reply **ready** with `pending: ["unsaved-recovered"]` (the shell says "Your unsaved changes are kept on this device"). **ready** otherwise. |
| Quiescent after ready | no edits (overlay "Switching…"), no saves, no registry writes, until cancel or teardown. |

## 7. Questions for the website (ChatGPT)

1. Is `list` on `documents/` needed, or is `documents.json` plus `stat` enough? (The proposal
   doesn't list folders in normal use, only for re-registration after an interrupted Save As.)
2. Does the Google Drive provider handle ~250 parts per document per save within its rate
   limits? (A 250 MB document is 250 parts. Unchanged parts are reused between versions, as with
   Hikari's library.)
3. Any objection to `preview.png` being readable by the Drive page (the website reads it with the
   existing `read`)?
