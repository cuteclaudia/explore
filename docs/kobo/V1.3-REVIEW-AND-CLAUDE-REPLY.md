## Answers to the six questions

1. **Preferred connection:** agree to server-side selection per user **and app**. Preserve the current account-wide selection as a compatibility default until an app has an explicit preference. Connecting, verifying or reconnecting a provider must not silently change any app's preference or copy a library. Multiple saved accounts of the same provider should have distinct connection records when that support is added.
2. **Google Drive:** the existing implementation already uses the essential mechanism in **Option A**. Drive holds immutable uploaded objects. Private Netlify Blobs records map `user + connection + app + logical path` to the current object, hash and logical ETag. `onlyIfNew` and `onlyIfMatch` publish those mappings conditionally. This applies to *all paths*, including heads, manifests and `libraries.json`; it is not a check-then-overwrite of a mutable Drive file. In-process locks are an optimization, not the correctness mechanism.
3. **Folder:** keep the visible app-created Kōbō folder with the limited `drive.file` permission. It is a **logical** path layout in the website adapter: the present Drive implementation places flat immutable revision objects under the visible app folder and keeps the virtual directory tree in its private index. Do not rely on native Drive filenames being unique or matching a browsable `library/gen/...` tree. The private index must be backed up for recovery; Drive alone is not the full library mapping.
4. **Compatibility:** yes. Old clients continue using their selected connection and `library/`. Additive fields may be ignored. Do not advertise `contractVersion: "1.3"` until its complete agreed operation set is implemented. Do not expose OneDrive as usable before an actual adapter is ready.
5. **Multiple libraries:** agree to the proposed layout: keep `library/` as `main`, add `libraries/<full UUID>/`, a bounded CAS-updated `libraries.json`, and app-root `originals/`. Remember the active library **per device, user, connection and app**. This avoids one device unexpectedly changing another device's open library. Missing registry means the existing main library, never an automatic migration.
6. **Concurrency evidence — corrected after stronger testing:** the original live Google success was single-client verification, not a live two-device race. The independent worker test checked the final index and logical conflict responses, but that alone does not prove the backend refused the losing conditional write: the commit helper's later read-back can turn an already-accepted write into a reported conflict. A stronger raw-response check found that the **local Blobs emulator can accept both competing creates**. We therefore cannot use those earlier tests to certify distributed atomicity. The website now includes a diagnostic that directly races two conditional SDK writes with the same starting revision, checks that exactly one raw response says `modified: true` and one says `modified: false`, checks the winning data, then checks stale-write refusal. It touches only a temporary private index key. Google is readable but server-enforced read-only until this diagnostic **passes on the live Netlify backend** along with the Drive tests. A failed recheck removes writable verification. This diagnostic has been implemented and tested locally, not run on Claudia's live account. Please retain your read-only policy pending that result, and still run the joint two-device app acceptance afterward.

Tests: `node --test server/google-drive-concurrency.test.mjs server/verify-atomic-index.test.mjs`. Live action after deployment: Settings → Files & storage → Google Drive → Test connection. Success must explicitly include competing-save checks. A final surviving value alone is not a passing result.

## Clarifications needed before freezing v1.3

- **Readonly sources:** §3 currently requires `readOnly: false` even for `read/stat/list`, while §4 says a readonly provider can be copied *from*. Permit authorized reads from an available readonly source. Require writable status for writes and selection as a sync destination. Never permit cross-connection `remove`.
- **Safe explicit copy and resume:** use a stable copy/upload identity and a frozen committed source generation. Publish the destination head/manifest last using atomic create-only. A preflight “destination empty” check is insufficient. On a resumed existing part, read and verify its expected size/hash; skip only an exact match. A different existing part or destination head stops the copy without merging or overwriting. An incomplete transfer must never be labelled complete. Include original bytes/manifests, not just catalog references, before claiming a full library copy.
- **Registry validation/recovery:** cap `libraries.json` at 256 KiB and 256 entries; require full canonical UUIDs (plus reserved `main`), unique IDs, safe timestamps and display names of at most 100 Unicode code points without control characters. Derive paths from validated IDs; do not trust arbitrary JSON paths. Preserve implicit `main` when creating the first registry. A CAS loser re-reads and reapplies its own change with bounded retries. Keep unfinished creation recoverable if the first head succeeds but registry registration fails. Hide/unhide should preserve identity and never delete original bytes; hiding main is an app UI choice, not a privacy boundary for older clients.
- **Switch lifecycle:** save local changes and settle pending sync before explicit library/provider selection. If sync is offline or conflicted, keep the old namespace intact and offer a clear choice rather than dropping edits. Define reply/change/relaunch ordering so an iframe is not destroyed before receiving its selection result. Mint a fresh launch only after checking the current account and app permission. Logout still closes private content immediately and must not automatically reopen an app. Automatic relaunch is a separate website follow-up, not something this review claims to have delivered.
- **Fresh authorization:** the website must check ownership, app permission, availability and target writability on every operation. A supplied `connectionId` is an authorized target selector, never a credential or proof of permission. Reject stale selection requests rather than silently mapping them to a newly reconnected account. Keep 1 MiB operations and all existing path, size and concurrency bounds.

With those clarifications, I approve the design direction and §5 folder layout. Please incorporate them into the next contract draft before we call v1.3 agreed/frozen. Photo sync can proceed now under v1.2.1; the library switcher can proceed once the registry and switching rules above are incorporated. Website multiple-connection implementation will be coordinated separately.

## Live diagnostic follow-up: SDK HTTP 409 handling

Claudia's production check passed the initial create-only phase, then reported CAS `2 reported accepted, 0 refused`, with raw backend HTTP `200, 409`. This identified a compatibility bug: `@netlify/blobs` 11.1.6 reports conditional HTTP 409 as `modified:true` because it only recognizes 412 as a refusal. This live result is different from the local emulator accepting both writes with HTTP 200.

A narrow Blobs fetch adapter now translates conditional-PUT 409 to 412 for the SDK, while the diagnostic retains the raw HTTP statuses. The actual index write path uses the same adapter, not just the test. The unchanged atomic probe passes against a real-SDK fixture reproducing 200/409; stale writes remain conflicts and never replace the winner. Nonconditional requests and other statuses are unchanged. All 125 website tests and packaged build checks pass. The complete live verification must be rerun; no production pass or full two-device acceptance is claimed yet, and the server's readonly gate remains in place until that pass.
