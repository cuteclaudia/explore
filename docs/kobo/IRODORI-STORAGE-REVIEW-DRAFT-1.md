# Irodori storage proposal: website review of draft 1

28 October 2026, Australia/Sydney. Review of Claude's supplied draft, not approval to enable storage or implement v1.4. Irodori 0.16.0 has **no storage bridge**. Hikari's actual two-device acceptance remains first. Runtime stays v1.2.1; the frozen v1.3 contract and proposed v1.4 switch/Drive design are unchanged.

**Decision: the per-document generation/CAS approach fits the existing operations, with revisions required below before implementation.** “No new operation” does not mean no website work: registry checkpoint coverage and index capacity need changes before enabling Irodori storage.

## Answers to §7

1. **Registry plus head checks are enough for normal browsing.** Read/validate `documents.json`, derive `documents/<uuid>/head.json`, and use stat/read with the appropriate conditional ETag. A missing head means unavailable, never create-on-open. `list('documents')` is needed if you promise discovery of orphaned committed UUIDs with no registry entry and no surviving local journal. Both existing providers list direct directories. Keep that a bounded, explicit reconciliation operation, not a crawl on every Open/Drive view. Current listing responses allow at most 2,048 direct children and have no bridge pagination; many retained orphan directories can exhaust that even with a 1,000-entry registry. Google directory listing currently scans private app-index records, so it is not a cheap replacement for a registry. Ordinary website Drive browsing must remain read-only and must not re-register documents by writing the registry.
2. **The transport supports many sequential ≤1 MiB puts; a 250-part production save is not yet certified.** The shell permits at most four concurrent storage operations. Start with two uploads and cap at four; use bounded jittered backoff, respect retry metadata, and persist resumable progress per scope. Google may throttle individual accounts/projects and every part causes more than one provider/index operation. Do not promise a fixed save time or quota. A rewritten compressed `.pcraft` can move byte boundaries, so even a small edit may replace most parts; unchanged-part reuse must be verified, not assumed. Run interrupted/resumed and competing 200–250 MiB real-document saves on both providers, verify full hashes, record throughput/429s/retries, and refuse oversized serialization before allocating/uploading it. Use precise units: 250 MiB is 250 1-MiB parts; decimal 250 MB is 239 such parts, rounded up. The existing ceiling is 256 MiB, not an unlimited decoded-layer budget.
3. **A private preview is suitable for a future website Drive adapter, with scope and version binding.** The website may use existing authorized reads for that user's app/connection; it must not expose a public preview URL, credentials, raw Drive ids or another app's namespace. `preview.png` must be treated as untrusted input: validate PNG signature and bounded bytes/dimensions, re-encode/decode safely, and use `image/png`/nosniff or a private blob URL. Missing previews get a placeholder, not an unavailable-document error. Prefer a committed logical `preview.png` inside the same generation/head, or an immutable per-generation preview referenced with generation/hash and checked against the head. A mutable fixed-name preview updated independently can show a stale/losing save and cannot be made transactionally consistent with the head by a separate CAS alone. Do not parse/render HTML/SVG as a PNG. The website Drive page/v1.4 reader is still a proposal, not delivered by approving this file layout.

## Required changes to the proposal

### Connection isolation and realistic recovery wording

Browser documents, cached originals/previews, recovery records, upload journals, recent lists and in-memory tasks must be scoped by **account + connection + app + document UUID**. Guest is separate. Per-account `doc-<hash>` alone is insufficient when switching kDrive and Google Drive or multiple connections.

Replace “a closed tab or lost connection loses nothing” with best-effort recovery wording. Recovery writes can fail, browser storage may be denied/evicted, a device can be lost, and a 1 GiB cache is not safe on every device. Check persistence/quota conservatively; evict only reproducible clean cache entries. Dirty/recovery documents must never be LRU-evicted. Save recovery before offering leave-ready with `unsaved-recovered`; if that write fails, remain busy and offer export. Keep a durable dirty branch until an actual verified save or explicit Discard. A recently uploaded file or registry attempt alone is not proof of success.

### Read-only and conflict behavior

Read-only means no `put`, including Save As and Save a Copy on that same connection. Open/read/Export and device-local copies remain available. Saving to a different verified writable destination requires an explicit destination and the relevant implemented connection-targeting support; no implicit provider switch or writable fallback.

Save As / Save a Copy allocate a fresh UUID and publish the new head with create-only. Parts and immutable preview first, conditional head last, then registry CAS. Save a Copy does not change the active document or its save target. If registry publication fails after the document head succeeds, report “document saved; listing update pending”, retain a scoped reconciliation journal and retry the same UUID. Never silently create another UUID or rewrite a different existing head after a lost response. Re-read and verify a potentially successful commit by generation, size and content hashes before declaring success.

Compare the logical `document.pcraft` checksum/content against the last synced document, not just a head ETag or serialized head JSON: a new generation alone is not proof of a user edit. Account for serialization-only timestamps/view state rather than treating every reserialization as a meaningful change.

“Replace with mine” requires the user's explicit choice after seeing a conflict, followed by a fresh head read and one conditional publication against that exact revision. Another race returns to conflict; do not automatically replace the newer branch on subsequent retries. Registry retries may replay the intended entry operation on freshly validated content, bounded to five attempts; they must not resend an old whole registry and erase another device's entries.

### Registry/head validation and ordering

- Enforce both the 256 KiB encoded-byte limit and 1,000-entry limit; a thousand 100-code-point Unicode names may exceed the byte limit. Refuse safely before publication, preserve work and show the cause.
- Unique canonical lowercase UUID-v4 IDs, plain-text names (no controls), safe nonnegative integer sizes, bounded positive dimensions and valid timestamps. Registry-supplied sizes/paths never authorize allocations or resource access; derive paths from validated ids. Reject duplicate ids, malformed roots and corrupt registries rather than replacing them with an empty registry.
- Validate `head.json` using the existing bounded generation schema, all names/paths/counts/totals/hashes, and the logical `document.pcraft` file allowlist plus any agreed preview file. Check memory bounds before assembling the file. Validate decoded image dimensions/layers/expanded memory independently; a 256 MiB compressed file is not necessarily safe to decode.
- An absent registry may be initialized create-only only for a writable explicit Save As/reconciliation. Missing/invalid registry on an explicit open must not create an empty document or fall back to an unrelated one.
- An orphan head with only `document.pcraft` cannot necessarily recover the human name lost with its registry. Define a bounded embedded name or an explicit “Recovered document <UUID>” fallback; do not promise that listing unknown heads reconstructs names.
- Renaming/hiding are registry changes; deletion/GC remain out of scope. Never remove generation parts or browser recovery because a registry retry failed.

### Website capacity and backup blockers

The current private Google index recovery snapshots are capped at **4,096 records and 2 MiB per app/connection**, including retained generations/directories. Around sixteen 250-part fully rewritten generations can approach the record limit; the byte limit can be reached earlier. A 1,000-document registry does not imply the website can currently back up that many documents. Existing checkpoint failure deliberately blocks head publication. Do not bypass that guard.

Before enabling this storage design, agree and test bounded incremental/chunked index backup capacity (or a much smaller explicitly enforced app-wide budget). Raising the per-document 256 MiB ceiling or silently increasing whole-request snapshot size is not a fix. No cleanup/GC is authorized by this review.

The current backup trigger recognizes `head.json` and `libraries.json`, **not `documents.json`**. Since document heads publish before registry entries, the head snapshot alone misses a subsequent new name/rename/hide. Add and test automatic registry checkpoint coverage before treating Irodori's index as recoverable. Include a full lost-index restore of multiple documents, registry names/hidden flags, previews and original bytes. This is website implementation work, not a new bridge operation, and is not delivered by the owner-only no-storage preview.

### v1.4 adapter

The proposed resource `documents/<uuid>` is sensible; validate it both server-side and in-app and require fresh app/connection authorization. Explicit missing/deleted opens never create, copy, overwrite or silently select another resource. Display sizes/dates from the registry are not authoritative for reads/allocations.

Keep prepare-to-leave/open integration pending v1.4 agreement. A busy registry commit/upload or genuine unsaved/conflicted branch blocks leaving. Recovery-backed ready requires successful durable recovery, explicit user consent, a request-bound held ready state and quiescence until cancel/teardown. Scope the receipt to the current account/connection/document and reject stale receipts. The website preflights and freshly authorizes the target before destroying the old app; a target failure cancels leave and preserves interaction. Logout/revocation still tears down immediately. Do not announce v1.4 or invent runtime support in this 0.16.0 preview.
